# 重构总结 - 从 LangGraph 到 LangChain

**日期**: 2026-08-20  
**决策**: 摒弃 LangGraph，全面拥抱 LangChain

---

## 📋 重构动机

在调研过程中发现，对于**固定顺序的业务工作流**，LangGraph 引入了不必要的复杂度：

### LangGraph 的问题

1. **状态管理复杂**
   - `TypedDict` + `Annotated[type, reducer]` 学习曲线陡峭
   - 增量更新模式不够直观（`return {"issues": [...]}` 会自动合并）
   - 需要理解 reducer 函数的合并逻辑

2. **过度设计**
   - 条件路由（`add_conditional_edges`）对简单顺序流程是过度抽象
   - StateGraph 的节点-边定义繁琐
   - SqliteSaver 检查点对非交互场景意义不大

3. **调试困难**
   - 状态合并是隐式的，不容易追踪
   - 错误发生时，难以定位是哪个 reducer 的问题

### 业务场景特点

我们的工作流：
- ✅ 固定的 7 个业务步骤（顺序执行）
- ✅ 非交互式（一次性运行完成）
- ✅ 错误继续执行，最后统一报告
- ❌ 不需要复杂的条件分支
- ❌ 不需要循环或回退
- ❌ 不需要暂停/恢复

**结论**: LangGraph 的强大能力在这里用不上，反而增加了复杂度。

---

## 🎯 新架构设计

### 核心理念

1. **简单优先** - 使用 LangChain 的 `RunnableSequence` 组合节点
2. **显式状态** - 通过 Pydantic 的 `WorkflowContext` 对象传递状态
3. **直接修改** - 节点直接修改 context，不用 reducer
4. **按需复杂** - 只在必要时（如需要分支）才引入 `RunnableBranch`

### 架构对比

| 组件 | LangGraph（旧） | LangChain（新） |
|------|----------------|----------------|
| 状态定义 | `TypedDict` + `Annotated` | `Pydantic BaseModel` |
| 状态传递 | 增量更新 + reducer | 直接修改对象 |
| 工作流定义 | `StateGraph` + edges | `RunnableSequence` |
| 节点实现 | 返回状态字典 | 修改 context，返回输出 |
| 错误处理 | 通过 issues + 路由函数 | 抛出 `WorkflowTerminated` |
| 持久化 | SqliteSaver | 不需要（可选） |

## 💡 核心改进

### 1. 状态管理简化

**旧代码（LangGraph）**:
```python
from typing import Annotated
from operator import add

class WorkflowState(TypedDict):
    issues: Annotated[list, add]  # 自动合并
    node_statuses: Annotated[Dict, merge_node_statuses]

def execute(state: WorkflowState) -> WorkflowState:
    # 返回增量更新
    return {
        "issues": [new_issue],  # 会被 add() 合并到已有 issues
        "node_statuses": {self.node_id: status}
    }
```

**新代码（LangChain）**:
```python
from pydantic import BaseModel

class WorkflowContext(BaseModel):
    issues: List[Issue] = []
    completed_nodes: List[str] = []

def process(context: WorkflowContext) -> NodeOutput:
    # 直接修改
    context.issues.append(new_issue)
    context.completed_nodes.append(self.node_id)
    
    return NodeOutput.create_success(...)
```

**优势**:
- ✅ 不需要理解 Annotated 和 reducer
- ✅ 修改是显式的，容易追踪
- ✅ Pydantic 提供类型验证和辅助方法

### 2. 工作流定义简化

**旧代码（LangGraph）**:
```python
workflow = StateGraph(WorkflowState)
workflow.add_node("node_00", Node00())
workflow.add_node("node_01", Node01())
workflow.set_entry_point("node_00")
workflow.add_conditional_edges(
    "node_00",
    should_continue,
    {"continue": "node_01", "end": END}
)
workflow.add_edge("node_01", END)

runnable = workflow.compile(checkpointer=SqliteSaver(...))
```

**新代码（LangChain）**:
```python
workflow = (
    Node00Input()
    | Node01FillBasic()
    | Node02FillPublication()
    # ... 更多节点
)

# 运行
result = workflow.invoke(context)
```

**优势**:
- ✅ 一目了然的顺序流程
- ✅ 不需要手动定义边和路由
- ✅ 代码量减少 70%

### 3. 错误处理简化

**旧代码（LangGraph）**:
```python
def should_continue(state: WorkflowState) -> Literal["continue", "end"]:
    critical_errors = [i for i in state["issues"] if i["level"] == "critical"]
    if critical_errors:
        return "end"
    if not state["records"]:
        return "end"
    return "continue"

workflow.add_conditional_edges(
    "node_01",
    should_continue,
    {"continue": "node_02", "end": END}
)
```

**新代码（LangChain）**:
```python
# 在 BaseNode.__call__() 中自动处理
if output.success is False and has_critical:
    raise WorkflowTerminated("检测到严重错误")

if not context.records:
    raise WorkflowTerminated("没有记录可处理")
```

**优势**:
- ✅ 不需要为每个节点定义路由函数
- ✅ 异常机制更符合 Python 习惯
- ✅ 终止逻辑集中在基类，节点无需关心

class Node01FillBasic(BaseNode):

## 🎓 经验教训

### 何时使用 LangGraph

✅ **适合使用** LangGraph 的场景：
- 复杂的条件分支（3个以上分支点）
- 需要循环执行节点
- 需要人工审核点（暂停/恢复）
- 多条并行执行路径
- 需要版本管理和检查点

❌ **不适合** LangGraph 的场景：
- 固定的顺序流程（如 ETL、数据处理管道）
- 非交互式的批处理任务
- 状态简单、不需要复杂合并逻辑

### 设计原则

1. **从简单开始** - 先用 LangChain，需要时再升级
2. **不要过度抽象** - 框架能力强不代表要全用上
3. **适配业务场景** - 工具服务于业务，不是反过来
4. **保持灵活性** - 新旧并存，验证后再迁移
